### C. 技能 / 爆炸 / BOSS 施放 · 屏震與頓幀（本輪主體）
- **問題**：此前**只有暴擊**觸發震屏 / 頓幀；`damage_dealt` 是**逐單位**信號 ⇒
  AoE 打 10 個敵人發 10 次信號，震屏取 max ⇒ 實際只有 1.5px（大 AoE 反而被拖平）。
- **方案**：另開 `EventBus.screen_impact(position, strength, hit_stop)` 表達**單次衝擊事件**，
  與命中目標數解耦。消費方 = `JuiceFX._on_screen_impact()`（震屏 + 頓幀，頓帧复用既有去重）。
- `GameConstants` 新增（`SHAKE_DECAY_PER_SEC` 之後）：
  `SHAKE_IMPACT_SKILL_BASE=2.5` / `SHAKE_IMPACT_SKILL_MAX=4.5` / `SHAKE_IMPACT_RADIUS_REF=80.0`
  （= 當前 `skills.json` 最大 `radius`，雷暴） / `SHAKE_IMPACT_EXPLOSION=4.5` / `SHAKE_IMPACT_BOSS_CAST=5.5`；
  頓帧 `HIT_STOP_IMPACT_SKILL=0.03` / `_EXPLOSION=0.05` / `_BOSS_CAST=0.06`
  （全部落在 Playground 建議的 30–60ms 帶內）。
  靜態函數 `shake_strength_for_radius(radius)`：線性插值 + `clampf` 兩端夾取（**唯一**一處實現）。
- **發射點（3 處，語義刻意不同）**：
  1. `skill_controller.gd::_execute_aoe` —— 玩家 AoE，**只在命中 ≥1 目標時**發
     （揮砍打空不給頓帧，否則連招發澀）；強度按 `data.radius` 分級。
  2. `ground_area.gd::_resolve_impact` —— 隕石落地爆發（世界事件），**無條件**發。
  3. `enemy_base.gd::_aoe_impact` / `_cone_impact` —— BOSS 踐踏 / 扇形重擊（世界事件），
     **無條件**發（放在圈內判定**之前** ⇒ 玩家走位躲開時地面照樣抖）。
- 驗證：`verify_juice` 新增 **H 段（9 條斷言）**：常量帶內 / 遞增、半徑分級單調 + 夾取、
  JuiceFX 確有連接（非死鉤子）、端到端（emit → time_scale<1 + offset 抖 → 自動復原）。

- 失敗兜底：`_decal_tex == null` ⇒ 退回代碼圓，與引入貼圖層前**逐位一致**（不崩、不靜默畫錯）。

## 追加④：命中頓幀 · 按傷害分級（Playground「重擊/技能命中定格稍久」）

### 問題
- 此前頓幀只有兩路：① **暴擊**（固定 `HIT_STOP_DURATION` = 30ms）② **衝擊事件**（技能/爆炸/BOSS，按**事件類型**）。

## 追加⑦：退出告警定位 —— `AudioStreamPlaybackWAV leaked`（測試環境產物）

> 段 K 收線時冒出的 `5 ObjectDB leaked` / `2 resources still in use`，本輪**定位並清零**。

### 定位過程（值得記：靠「分類 + 對照組」而不是靠猜）
1. **連跑 3 次 ⇒ 計數浮動（3 / 5 / 3）** ⇒ 不是穩定泄漏，是**時序**問題。
2. **`--verbose` 讀類型** ⇒ 泄漏物**只有音頻類**：`AudioStreamPlaybackWAV` ×2 + `AudioStreamWAV` ×1，
   資源 `res://data/audio/boss_phase.wav`。**沒有任何節點** ⇒ 與「孤兒節點」類泄漏（坑 51）**不同源**。
3. **對照組**：`verify_juice` / `verify_shop` / `verify_summon` **乾淨**，`verify_loot` 報
   ⇒ 差異 = 「退出前播過音效」（段 F/I/J/K 播 `pickup_gold` / `boss_phase`）。

### 根因
`AudioManager.play()` 是「播放即焚」（`finished` → `queue_free`），但
**headless 用 Dummy 音頻驅動、播放頭根本不推進** ⇒ `finished` 永不觸發 ⇒ 播放器一直掛在 `tree.root`。

### 先做了「逐場景收尾」，但**掃全庫後改為集中修**（關鍵決策）
- 第一版：`AudioManager.stop_all()` + `VerifyWatchdog.stop_sfx()`，在 `verify_loot._finish()` 裡收尾。
  - ⚠️ **二次坑**：只 `stop()+free()` 不夠 —— 加打印確認過「根節點播放器數 2→0」，
    `AudioStreamPlaybackWAV` **照樣漏**。因為 `stop()` 只把 playback 從 AudioServer 活躍列表摘掉，
    **真釋放發生在混音線程的下一次混音**。
  - 實測對照：不等 ⇒ **~2/3** 概率漏｜`await` 2 幀 ⇒ ~1/5 **仍不穩**｜
    `await` **0.2s 真實時間**（`create_timer(0.2, true, false, true)`）⇒ **12/12 全清零** ✅
  - ⇒ 教訓：**混音按真實時間推進，與 `process_frame` 幀數無關**。
- **但掃了全庫 77 個 `verify_*` ⇒ 21 個都在報**（`verify_audio66`/`verify_boss63`/`verify_e2e`/
  `verify_hud`/`verify_settings`/`verify_class_select`…）⇒ 逐個加收尾 = 改 21 個文件，**是雜活**。

### 最終方案：**在 `AudioManager.play()` 源頭跳過**（1 處改動，21 個場景一起乾淨）
```gdscript
static func _is_silent_runtime() -> bool:
    if not AudioServer.has_method("get_driver_name"):
        return false                      # 老版本兜底：拿不到驅動名就照常播放
    return String(AudioServer.call("get_driver_name")) == "Dummy"
```
`play()` 裡加 `if _is_silent_runtime(): return`。
- **判據用「音頻驅動名」而不是 `DisplayServer`**：真正的病根是「播放頭不推進」，
  而 `--audio-driver Dummy` 在**有窗口**時也能觸發同樣的泄漏。
- 無頭下本來就聽不到聲 ⇒ **不創建播放器才是正確行為**；有窗口的真實遊戲行為**逐位不變**。
- 保留 `AudioManager.stop_all()`（真·有用 API：切場景全靜音 / 給跑在**有窗口**下的
  `capture_*` 抓圖工具收尾）與 `VerifyWatchdog.stop_sfx()`（同上，已文檔化）。
- `verify_audio66` 段 D **同步改口徑**（原本 `after >= before` 會被「跳過」掩蓋成廢斷言）：
  按 `_is_silent_runtime()` 分叉 —— Dummy 下斷言「不創建播放器」，真實驅動下斷言「掛載播放器」。
  ⇒ 教訓：**改了被測物的行為，就要回去看那條斷言還測不測得到東西。**

## 追加⑧：段 K 收線時挖出並修掉的**兩個真問題**

### 問題 1：彈出動畫會**覆蓋**外部寫入的位置（真缺陷，非測試問題）
- **症狀**：`verify_e2e` 段⑦ 把掉落物瞬移到玩家腳下後，**撿不到**（報「背包沒增長」）。
- **根因**：`_advance_pop` **每帧都寫 `global_position`** ⇒ 段⑦ 那次瞬寫**當場被覆蓋**，
  掉落物被彈回拋物線 ⇒ 永遠到不了玩家腳下。
  （與「磁吸搶寫」是同一個坑，但磁吸有顯式叫停、**外部寫入沒有**。）
- **修法（通用兜底）**：記「上一帧自己寫下的位置」`_pop_written`，
  `_process` 裡發現 `global_position != _pop_written` ⇒ 判定「別人插手」⇒ **動畫立刻讓位**（`_pop_elapsed = -1`）。
  - 語義：**pop 只在「沒人碰」時才擁有位置**。比「只認磁吸一個特例」健壯得多
    （未來任何調用方 / 擊退 / 傳送都自動兼容）。
  - 斷言（`verify_loot` 段 K 新增 ⑧）：外部寫 (200,200) 後 ⇒ `_pop_elapsed < 0` 且位置**保持** (200,200)。
  - ⚠️ **踩坑**：`SceneTree.process_frame` 是在節點 `_process` **之前**發出的 ⇒
    只 `await` 一帧讀到的是「剛寫完、掉落物還沒跑 `_process`」的中間態 ⇒ **假紅**。
    **必須等兩帧**（第一帧讓出、第二帧才在 `_process` 跑完之後）。

### 問題 2：`verify_e2e` 段⑦ 的**既有偶發假紅**（A/B 證明與本輪無關）
- **症狀**：`⑦ 拾取后会话背包增长（1 → 1）`，**時紅時綠**。
- **定位**：段⑤ 刻意把玩家**瞬移到怪物重心**（註釋「保證掉落都落在附近，便於後續拾取」）⇒
  段⑥ 殺怪時掉落**落在玩家腳下** ⇒ 只要 `LOOT_POP_DELAY`（0.25s）一到就被**自動撿光**
  ⇒ 段⑦ 無物可撿。而段⑥ 只 `_wait_frames(10)`，
  **10 帧的真實耗時隨機器負載浮動**（慢機上 > 0.25s）⇒ 偶發。
- **A/B 實證**（把 `enemy_base` 的 `pop_from` 註掉 = 關掉彈出動畫）：
  | 臂 | 結果 |
  |---|---|
  | 關掉彈出動畫 | 8 次**紅 2 次**（≈25%） |
  | 開著彈出動畫 | 8 次**全綠** |
  ⇒ 結論：**這是既有問題**，且本輪的彈出動畫**反而降低**了它的復現率（延後了自動拾取）。
- **修法**：段⑤ **不再挪玩家**（那一步對拾取毫無貢獻 —— 段⑦ 本來就會把掉落物瞬移到玩家腳下），
  玩家留在關卡自己的出生點 ⇒ 掉落離玩家遠 ⇒ 段⑥ 必然不誤撿 ⇒ 段⑦ 確定性成立。
  - 修後**連跑 10 次全綠**。
