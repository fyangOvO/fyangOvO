## 一、现状盘点（2026-09-24 全量实读）

### 1.1 传奇特效系统：完整实现，零调用

`scripts/legendary/legendary_effect_system.gd`（216 行）实现了三要素范式：

| 层 | 状态 | 证据 |
|---|---|---|

| **注册** | ✅ 完整 | `register()` / `unregister()` / `clear()` |
| **触发结算** | ✅ 完整 | `on_event(trigger_type, ctx)` —— 遍历注册表、概率、冷却、阈值、叠层、效果解析 |

### 1.3 送上门的好消息：接线口已经全部现成

`EventBus` 已有三个**正好对应特效 trigger 的战斗信号**，且都已在战斗侧正常 emit：

| EventBus 信号 | 签名 | 已有 emit 点 | 对应特效 trigger |
|---|---|---|---|
| `damage_dealt` | `(target, amount, is_crit, element)` | `skill_controller.gd:180`（**含 `is_crit`**）| `on_hit` / `on_crit` |
| `damage_taken` | `(source, amount, element)` | 敌人攻击玩家处 | `on_damage_taken` |
| `unit_died` | `(unit, killer)` | `health_component.gd:287` | `on_kill` / `on_elite_kill` |

**⇒ 这意味着接线成本极低**：一个「特效总线」监听这三个信号 → 翻译成 `ctx` → 转发 `on_event()`。
不需要改动任何伤害管线、不需要碰 `DamageCalc`、不需要改敌人逻辑。

## 二、第 1 块 · 传奇特效接线（**本步最高优先级**）

### 2.1 设计原则

1. **不改战斗管线**。接线全部靠「监听 EventBus → 转发」，不动 `DamageCalc` / `take_damage`。
2. **结算与执行分离**。`on_event` 已经设计成「只算不改状态」（类注释明写），执行方必须有明确归属。
3. **单局内存态**。叠层 / 冷却不入存档（与现有实现一致）。
4. **可观测**。每条特效触发时必须可见（飘字 / 特效 / buff 图标），否则等于没做。

### 2.2 接线架构（指名方向）

**新增一个「特效总线」节点**（建议 `scripts/legendary/legendary_bus.gd`，挂到关卡场景）：

```
EventBus.damage_dealt  ──┐
EventBus.damage_taken  ──┼──► LegendaryBus ──► LegendaryEffectSystem.on_event(trigger, ctx)
EventBus.unit_died     ──┘                          │
                                                    ▼
                                          Array[结算结果]
                                                    │
                     ┌──────────────────────────────┼──────────────────────────┐
                     ▼                              ▼                          ▼
              deal_damage → 调目标 take_damage   heal → 玩家回血        buff_stat → 挂增益组件
```

**职责边界（必须写死，否则会重蹈覆辙）**

| 组件 | 职责 | 禁止 |
|---|---|---|
| `LegendaryBus` | ① 关卡进入时 `register()` 全部已穿装备（含词缀绑定+底材绑定的特效）② 监听 EventBus 三个信号 ③ 把信号翻译成 `ctx` 字典 ④ 调 `on_event()` ⑤ **执行**返回的结算结果 | 不得自己算伤害 / 不得直接改玩家 HP 字段（要走正规接口）|
| `LegendaryEffectSystem` | 纯结算：概率 / 冷却 / 阈值 / 叠层 / 数值解析 | 不改任何游戏状态（**保持现有设计，勿破坏**）|
| 战斗侧 | 正常走原管线 | 不得直接调 `on_event`（统一走总线，避免多处重复触发）|

### 2.3 四个 trigger 的 `ctx` 契约（**工程侧必须按此填**）

`on_event()` 已实现的读取键如下——**填错键名会导致条件静默失效**（参考第二步前缀池的教训）：

| trigger | 必需 ctx 键 | 来源 | 缺失后果 |
|---|---|---|---|
| `on_hit` | `attack`（玩家攻击力）| `player.get_attack_damage()` | `deal_damage` 算成 0 |
| `on_crit` | `attack` | 同上 | 同上 |
| `on_damage_taken` | `max_hp` | `player.health.max_hp` | `heal` 类效果按默认 100 算，严重偏低 |
| `on_low_hp` | **`hp_pct`**（0–1 比值）+ `max_hp` | `player.health.hp / max_hp` | ⚠️ **阈值判定失效**——`hp_pct` 缺失时默认 `1.0`，永远大于 `hp_below_pct`，**特效永不触发** |
| `on_kill` | 无必需键 | — | — |
| `on_elite_kill` | 无必需键 | — | 需先定义「精英」判定（见 §2.5）|
| `on_block` | 无必需键 | — | **⚠️ 无格挡系统**，见 §2.5 |
| `on_skill_cast` | 无必需键 | — | 需在 `try_cast()` 末尾埋点 |
| `on_resource_spend` | **`amount_spent`** | `data.mana_cost` | 阈值判定失效 |
| `on_pickup_gold` | 无必需键 | — | 需在金币拾取处埋点 |

> **⚠️ `hp_pct` 这一条是最容易踩的坑**：它缺失时 `on_low_hp` 类特效（`qi_jie_zhi_guan` 濒死叠层、
> `bu_xiu_zhe_de_can_qu` 不死者残躯、`fu_su_sheng_ming_jie` 复苏生命）**全部静默失效**，
> 且不会报错。工程侧必须在 `ctx` 里正确填 0–1 比值（不是百分数 0–100）。

#### 2.5.1 格挡系统现状（**实测修正**）

**结论：格挡系统不是「没有」，而是「做了但没广播」。**

| 层 | 状态 | 证据 |
|---|---|---|
| 减伤常量 | ✅ 已有 | `game_constants.gd:1027` `BLOCK_DAMAGE_REDUCTION = 0.5` |
| 玩家格挡率 | ✅ 已实现 | `player_controller.gd:582` `get_block_chance()` = `PLAYER_BASE_BLOCK_CHANCE + _combat_stats["block_chance"]` |
| 判定逻辑 | ✅ 已接线 | `health_component.gd:131` `if _roll_block(): dmg *= 1.0 - BLOCK_DAMAGE_REDUCTION` |
| 属性管道 | ✅ 已通 | `stat_calculator.gd:128` `"block_chance"` 在 `direct` 表内 |
| **事件广播** | ❌ **缺失** | `_roll_block()` 返回 `true` 后**没有 emit 任何信号** ⇒ 外部无从知晓「刚刚格挡了」 |

**⇒ 所以 `shou_hu_jian_bi`（格挡回血）的落点缺口极小**：只需在 `_roll_block()` 命中处补一个事件，
不需新建整套格挡机制。这比第三轮预估的「新增格挡系统」便宜一个数量级。

### 2.7 两个「缺系统」的效果类型（**本步最大工程量** · 2026-09-24 拍板：**两个都做**）

> 用户裁定：临时增益系统 **做**、召唤物系统 **分期做**。以下两个子节为设计方向。

#### A. 临时增益系统（`buff_stat` / `ms_boost` / `damage_reduction`）

现状：**无任何「有时限的临时属性修正」机制**。玩家属性来自 `StatCalculator` 全量重算（装备+天赋+等级），
没有「临时 +20% 攻击，持续 5 秒」这种叠加层。

涉及特效：**9 条**（`kuang_lan_chao_xi_ren` / `you_an_yi_ying_pao` / `sui_jia_po_jun_quan` /
`xun_jie_ji_xing_tui` / `tie_bi_zhong_zhuang_tui` / `shun_ying_huan_bu_xue` / `wang_quan_tong_yu_zhui` /
`lie_jie_zhi_huan` / `tan_lan_ju_bao_jie`）+ 套装若干

**设计方案（指名方向）**

```
新增：BuffComponent（挂在玩家 / 敌人身上）
  · active_buffs: Array[{stat, value, expire_at, stacks, source_effect_id}]
  · 每帧清理过期项
  · 取属性时：StatCalculator 的最终值 + Σ(同类 buff)
  · 同名 buff 可刷新（取 max(剩余时间)）或叠层（按 source 定义）
  · 增益必须在 HUD 有图标（否则玩家不知道自己在增益中）
```

**关键约束**：
- 增益**不得写进存档**（单局态）
- 增益必须能叠加（`buff_stat` 的 `target: "enemy"` 是给敌人挂减速，不能影响到玩家属性）
- 敌人减速复用同一组件（敌人也挂 `BuffComponent`）

#### B. 召唤物系统（`summon`）

现状：**无召唤物**。敌人 `enemy_base.gd` 是完整 AI，但没有「友方 AI 单位」概念。
（注：`grep summon` 命中的 `enemy_base.gd` / `boss_phase_controller.gd` 是「BOSS 召唤小怪」，是敌方生成，非玩家召唤物。）

涉及特效：**3 条**（`an_shi_zhou_yin_shu` 暗影咒印书、`qi_chong_hui_xiang_zhi_guan` 七重回响之冠）
+ 第一步技能 `spirit_wolf` / `summon_elemental` **2 条技能**

**设计方案（指名方向）**

```
新增：SummonComponent 或复用 enemy_base 加「阵营」概念
  · 召唤物 = 有 AI 的友方单位：自动找敌、攻击、有时限
  · 需要：队伍/阵营字段（player / enemy），碰撞层与敌人互打
  · 需要：精灵素材（见 §六）
  · 召唤上限需限制（避免 3 条特效 × N 次触发刷屏）
```

> ⚠️ **这也解释了为什么 `on_event` 写好了却没人敢接线**：12 种效果里有 2 种需要整套新系统。

## 四、第 3 块 · 装备 × 技能联动（**本步新内容**）

> 这是本步相对前两步的**新增设计面**：让装备与技能产生真正的组合空间，
> 而不是「装备只加数值、技能只看倍率」。

### 4.1 联动设计总览（6 条联动线）

| # | 联动线 | 方向 | 依赖的既有机制 |
|---|---|---|---|
| L1 | **元素强化** | 装备 `elemental_damage` → 强化对应元素技能 | 第二步死钩子① |
| L2 | **技能等级** | 装备 `skill_level` → 提升技能倍率 | 第二步死钩子③ |
| L3 | **冷却缩减** | 装备 `cooldown_reduction` → 技能转得更快 | 第二步死钩子④ |
| L4 | **耗蓝缩减** | 装备 `skill_cost_reduction` → 技能更省蓝 | 第二步死钩子④ |
| L5 | **触发型联动** | 技能的 `on_skill_cast` / `on_crit` 触发装备特效 | 本步 §二 |
| L6 | **召唤物联动** | 技能召唤物 与 装备 `summon` 特效 共用系统 | 本步 §2.7B |

### 4.2 L1 元素强化（**联动核心** · 2026-09-24 拍板「拆 6 个子键」）

**现状问题**：第二步已定位——`DamageCalc.compute_hit` 第 5 形参（`elem_mult`）在两处调用点
**硬编码 `0.0`**：`skill_controller.gd:168`、`player_controller.gd:945`。
即：装备上的 `elemental_damage` 结算层已输出（`stat_calculator.gd:126`），但**永远传 0 进去**。

**拍板：元素伤害拆 6 个子键**（用户 2026-09-24 裁定，推翻第三步首稿的「不拆」建议）。

#### 4.2.1 元素体系现状盘点（**实测，含 4 处缺口**）

| 维度 | 现状 | 缺口 |
|---|---|---|
| 元素常量 | ✅ 6 种：`physical`/`fire`/`cold`/`lightning`/`poison`/`shadow` | — |
| **元素伤害加成** | 🟡 只有 **1 个总键** `elemental_damage`（`game_constants.gd:1325`）| ❌ **缺 6 个元素子键** ← 本次要拆 |
| **元素抗性** | 🟡 只有 **4 个**：`fire_resist` / `cold_resist` / `poison_resist` / `lightning_resist` | ❌ **缺 `shadow_resist`**（元素有 6 种，抗性只 4 种）|
| 元素抗性映射 | 🟡 `player_controller.gd:241` `_RESIST_KEY_BY_ELEMENT` 只映射 **4 种** | ❌ `shadow` / `physical` 取不到抗性（`get_resist` 返回 0.0）|
| 抗性减伤公式 | ✅ 已有：`resist / (resist + 50 × L)`（`RESIST_DR_CONSTANT_PER_LEVEL = 50`）| — |
| 异常状态映射 | 🟡 `AILMENT_ELEMENT_MAP` 只映射 **3 种**（毒→中毒 / 火→燃烧 / 冰→冰冻）| ❌ `lightning` / `shadow` 无异常 |

> ⚠️ **`shadow` 是「半成品元素」**：常量、技能、特效都在用（`shadow_blink` / `void_rift` /
> `shadow_volley` 三条技能 + 暗影类特效），但**既无抗性键、也无异常状态** ⇒ 暗影伤害对任何目标都是「全额穿透」。
> 这是一个**既有的平衡漏洞**，与本次拆键一起修。

#### 4.2.2 6 个子键的定义（**本步新增**）

**命名约定**：`elemental_damage_<元素>`（与 `_RESIST_KEY_BY_ELEMENT` 的映射风格一致）。

| # | 子键 | 对应元素 | 说明 |
|---|---|---|---|
| 1 | `elemental_damage_fire` | `fire` | 火焰伤害加成 % |
| 2 | `elemental_damage_cold` | `cold` | 冰霜伤害加成 % |
| 3 | `elemental_damage_lightning` | `lightning` | 闪电伤害加成 % |
| 4 | `elemental_damage_poison` | `poison` | 毒素伤害加成 % |
| 5 | `elemental_damage_shadow` | `shadow` | 暗影伤害加成 % |
| 6 | `elemental_damage_physical` | `physical` | 物理伤害加成 %（**语义等同「攻击强化」**，见下）|

**⚠️ 关于 `elemental_damage_physical` 的语义裁定（必须明确，否则会歧义）**

「元素伤害」在传统 ARPG 里**不含物理**。但既然要拆 6 个子键对应 6 种元素，物理必须有个归处。
建议裁定：**`elemental_damage_physical` 与 `pct_attack` 语义重叠 ⇒ 不新增该键**，
物理伤害走已有的攻击力/物理加成体系。**子键只做 5 个非物理元素**。

> ⇒ **实际新增 5 个子键**：`fire` / `cold` / `lightning` / `poison` / `shadow`。
> 若用户坚持 6 个，则 `elemental_damage_physical` 需与 `pct_attack` 做**互斥校验**（防双重加成）。

#### 4.2.3 取键口径（**接线规则，防口径分裂**）

```
技能施放时：
  e = data.element                                  # 6 种之一
  if e == "physical":
      elem_mult = 0.0                               # 物理不吃元素子键
  else:
      elem_mult = player.get_combat_stat("elemental_damage_" + e)   # 元素专精子键
                + player.get_combat_stat("elemental_damage")        # 通用元素加成（保留）
  DamageCalc.compute_hit(base, crit_chance, crit_dmg, e, elem_mult, ...)
                                                          ^^^^^^^^^ 由 0.0 改为变量
```

**兼容规则（不破坏既有词缀）**

| 规则 | 说明 |
|---|---|
| 通用 `elemental_damage` **保留** | 已有词缀（如套装霜噬 `elemental_damage: 15`）继续生效，作用于**全部非物理元素** |
| 子键与总键**累加** | `elem_mult = 专精子键 + 通用总键`，不是取代 |
| 物理**两者都不吃** | `elemental_damage` 与子键均对 `physical` 技能无效 |

⇒ 这样「通用元素流」（堆 `elemental_damage`，全能但低）与「元素专精流」（堆单元素子键，高但窄）
形成**两条词缀路线**，是拆键的主要收益。

#### 4.2.4 三套装与技能的自然联动（设计亮点）

| 套装 | 元素 | 天然适配技能 | 对应子键 |
|---|---|---|---|
| 霜噬（冰）| `cold` | `frost_nova` / `frost_bolt` | `elemental_damage_cold` |
| 烬途（火）| `fire` | `fireball` / `meteor` / `explosive_arrow` | `elemental_damage_fire` |
| 守誓者（坦）| — | `iron_bulwark` / `arcane_shield` | 无关（生存向）|

⇒ **穿霜噬 + 堆 `elemental_damage_cold` + 带冰技能 = 完整冰霜流**。
拆键让「套装 + 词缀 + 技能」三者能指向同一元素，这是装备特色玩法的核心体验。

#### 4.2.5 需同步补齐的两处元素缺口（**顺带修**）

| # | 缺口 | 影响 | 处置 |
|---|---|---|---|
| 1 | **缺 `shadow_resist`** | 暗影伤害无抗性可减 ⇒ 对一切目标全额穿透 | 新增 `STAT_SHADOW_RESIST` + 进 `stat_calculator` 的 `direct` |
| 2 | **`_RESIST_KEY_BY_ELEMENT` 缺 `shadow`** | `get_resist("shadow")` 恒返回 0.0 | 映射表补 `shadow → shadow_resist` |
| 3 | `AILMENT_ELEMENT_MAP` 缺 `lightning` / `shadow` | 雷/暗影攻击不产生异常状态 | 可选：雷→「麻痹」（减缓攻击速度）、暗影→「虚弱」（降攻击）；**本期可延后** |

> ⚠️ 第 1、2 项**必须与拆键一起做**，否则「暗影专精」将是一条**无抗性对应**的破格路线（伤害无处可挡）。

### 4.3 L2 技能等级（**跨步耦合，需第一步配合**）

第二步已定位：`skill_level` 是死钩子，且三处都缺：
1. `SkillData` 无 `level` 字段（仅 13 个 `@export`）
2. `stat_calculator` 的 `FINAL_KEYS` / `direct` 均不含 `skill_level`
3. `skill_controller.gd:161` 用裸 `data.multiplier`

**联动规则（指名方向）**

```
技能倍率 = data.multiplier × (1 + 0.08 × (level - 1))
                                     ↑ 第一步 §2.1 已拍板：L1=1.000 → L10=1.720

level 来源 = 技能自身等级（存档）+ 装备 skill_level 加成
```

**⚠️ 与第一步的耦合点**：第一步拍板「技能等级上限 10 / ×1.72 系数先落地」，

### 4.4 L3 / L4 冷却与耗蓝缩减（**口径统一**）

第二步已定位：
- `skill_controller.gd:116` 裸赋 `_cooldowns[id] = data.cooldown`
- `skill_controller.gd:113` 裸扣 `mana.try_spend(data.mana_cost)`

**联动规则（指名方向）**

```
实际冷却 = data.cooldown × (1 - cooldown_reduction / 100)，下限 0.2 秒
实际耗蓝 = data.mana_cost × (1 - skill_cost_reduction / 100)

⚠️ 下限必须存在：cooldown_reduction 若达 100% ⇒ 冷却为 0 ⇒ 无限连发 ⇒ 崩坏
⚠️ 减耗不下到 0 以下：负数耗蓝会变成回蓝，需 clamp 到 ≥ 0
```

> **策划红线**：冷却缩减**建议上限 60%**（对应最短 40% 冷却）。
> 若词缀可堆到 100%，必须有硬编码下限兜底——**这是防崩坏的必要保险，不是可选优化**。

### 4.5 L5 技能触发装备特效（**接线后的自然产物**）

接线完成后自动获得（无需额外设计）：

| 玩家行为 | 触发链 |

| 用技能暴击 | `skill_controller._hit()` → `damage_dealt(is_crit=true)` → `on_crit` → 烬誓·燃魄刃叠层 |
| 放技能 | `try_cast()` 埋点 → `on_skill_cast` → 七重回响之冠抽召唤 / 聚能奥术球叠层 |
| 放技能耗蓝 | `mana.try_spend()` 埋点 → `on_resource_spend` → 七重回响之冠召唤 |
| 技能反伤击杀 | `unit_died` → `on_kill` → 暗影咒印书召唤 |

⇒ **这就是「装备特色玩法」的体验来源**：技能是触发器，装备是效果器。

### 9.1 决策 1 · 格挡系统增强（**修正首稿误判**）

**首稿误判**：第三步首稿写「全库无格挡系统，需新增」⇒ **实测错误**。格挡系统完整存在
（`BLOCK_DAMAGE_REDUCTION=0.5` / `get_block_chance()` / `_roll_block()` / `block_chance` 已进属性管道）。

**实际要做的三件事**

| # | 改动 | 位置 | 为什么 |
|---|---|---|---|
| 1 | **新增「格挡成功」事件** | `health_component.gd:131` `_roll_block()` 命中处 | `on_block` 特效的落点；现有代码格挡后**静默减伤**，外部无从知晓 |
| 2 | **格挡率可被装备注入** | 已有（`_combat_stats["block_chance"]`）| 确认盾类装备词缀能提升格挡率 |
| 3 | **格挡减伤可被装备修正** | 新增 `block_damage_reduction` 统计键 | 允许「格挡强度」类词缀（现在 `BLOCK_DAMAGE_REDUCTION` 是硬编码常量 0.5）|

**格挡 vs 闪避的定位区分（设计说明）**

| 机制 | 效果 | 定位 |
|---|---|---|
| 闪避 `dodge` | **完全免疫**本次伤害 | 敏捷向 · 高风险高回报 |
| 格挡 `block_chance` | **减伤 50%**（可被装备修正）| 坦克向 · 稳定减伤 |

⇒ 守誓者套装（坦克流）应强化**格挡**而非闪避：`+block_chance` / `+block_damage_reduction`。

**事件契约（指名方向）**

```gdscript
# EventBus 新增（沿用现有命名约定：过去式 = 通知用）
signal block_succeeded(blocker: Node, source: Node, reduced_amount: float)
# 在 _roll_block() 返回 true 且已应用减伤后 emit
# ⇒ legendary_bus 监听此信号 → 转发 on_event("on_block", {}) → 触发守护·坚壁回血
```

> ⚠️ **命名注意**：现有 `_roll_block()` 是「判定」，事件应在**判定成功且减伤已应用**后发，
> 否则监听方读到的伤害值会是减伤前的。

### 9.2 决策 2 · 临时增益系统（**做** · 解锁 14 条）

| 存档 | **不入档**（单局态，与现有叠层/冷却一致）|
| 可视化 | HUD 必须显示 buff 图标 + 剩余时间（否则玩家不知在增益中）|

**⚠️ 三个必须守住的约束**

1. **`target: "enemy"` 的 buff 绝不能污染玩家属性**（`kuang_lan_chao_xi_ren` 是给敌人挂减速）
2. **增益不得写入存档**（否则重开游戏还带着 buff）
3. **同名 buff 的叠加模式必须显式声明**，不能默认（否则会叠到崩坏）

### 9.3 决策 3 · 召唤物系统（**分期做**）

用户裁定**分期**。完整设计见 §2.7B。

**建议的分期切法**

| 期 | 内容 | 产出 |
|---|---|---|
| **本期（第三步收尾）** | **定协议**：召唤物接口、阵营字段、上限规则、素材规格 | 文档 + 数据定义 |
| 一期 | **最小可用**：1 种召唤物（暗影仆从）跑通「召唤→自动找敌→攻击→时限消失」 | 解锁 `an_shi_zhou_yin_shu` 1 条特效 |
| 二期 | 扩展：回响体 + 2 条召唤技能（`spirit_wolf` / `summon_elemental`）| 解锁剩余 3 项 |
| 三期 | 召唤物吃装备加成 / 召唤物 AI 强化 / 多召唤物协同 | 追质感 |

**协议先行的理由**：召唤物涉及**阵营（player/enemy）**这一底层概念，
若不定协议就动手，很容易做成「技能召唤」和「装备召唤」两套互不相通的实现（第三步 §4.6 已警示）。

### 9.4 决策 4 · 元素拆 6 个子键（**拆**）

用户裁定**拆**。完整设计见 §4.2。要点：

| 项 | 结论 |
|---|---|
| 子键 | 新增 **5 个非物理子键**：`elemental_damage_{fire,cold,lightning,poison,shadow}` |
| `physical` | **不建子键**（与 `pct_attack` 语义重叠，避免双重加成）|
| 通用键 | `elemental_damage` **保留**，与子键**累加** |
| 取键规则 | `elem_mult = 专精子键 + 通用总键`；`physical` 两者都不吃 |
| **顺带必修** | ① 补 `shadow_resist` ② `_RESIST_KEY_BY_ELEMENT` 补 `shadow` 映射 |
| 可延后 | `AILMENT_ELEMENT_MAP` 补 `lightning`/`shadow` 异常（本期不做）|

> ⚠️ **`shadow_resist` 与拆键必须同批做**。否则「暗影专精」是**无抗性对应**的破格路线
> （暗影伤害对一切目标全额穿透，没有装备能挡）——这会直接破坏平衡。
>
> 若用户希望保留 6 个子键（含 `elemental_damage_physical`），需额外加「与 `pct_attack` 互斥校验」，
> 属可选分支，见 §11.1 附录。
