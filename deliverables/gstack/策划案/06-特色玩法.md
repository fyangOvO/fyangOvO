## 三、逐系统方案骨架

### 3.1 爬塔（Tower）

#### 3.1.1 设计意图

给**高阶玩家**一个「高风险高产出、不消耗章节进度」的循环。爬塔的产出侧重点是
**特殊装备**，而不是常规装备——所以塔内掉落表要与章节关卡**分开**。

#### 3.1.2 骨架结构

| 维度 | 骨架建议 | 待拍板点 |
|---|---|---|
| 塔的数量 | 1 座主塔（可扩展为 3 座，一职业一座） | **S1** |
| 层数 | 每层 = 一个关卡（复用 `LevelData`） | **S2** |
| 层数区间 | 建议 30 层（低层 1–15 普通票 / 高层 16–30 高级钥匙） | **S2** |
| 难度曲线 | 每 5 层一个台阶，层内 5 关同级 | **S3** |
| BOSS 分布 | 每 5 层的第 5 层 = BOSS 层（二阶段） | **S3** |
| 死亡规则 | 死亡即结束，已获得的特殊装备**保留**（待拍板） | **S4** |
| 退出规则 | 每层通关后可「继续 / 带出」，带出即结算 | **S4** |
| 重入规则 | 从已解锁的最高层重入 or 从第 1 层重入 | **S4** |
| 进度存档 | `save_data` 新增 `tower_progress` 字典 | — |

#### 3.1.3 与既有系统的接线点

- **复用**：`LevelData`（塔层以程序化生成关卡承载）、`LevelScene`、`LevelGenerator`
- **复用**：`LootRoller` + 新增塔专属 `loot_table`（`data/loot_tables/` 加一条）
- **新增**：塔层定义数据、入口面板、进度存档（`save_data.tower_progress`）、门票校验（`save_data.tickets`）
- **⚠️ 硬约束**：塔层的程序化生成会**每局重随机**（除非写 `layout.seed`）。
  若希望「同一层每次一样」，需给塔层写死 `layout.seed`。→ 见 **S5**

#### 3.1.4 ✅ S10 已拍板落地：`save_data.tickets` 字典

**新增字段**（`game/resources/save_data.gd`）：

```gdscript

**必须同批改的五项**：

| 序 | 文件 | 改动 | 风险 |
|---|---|---|---|
| 1 | `save_data.gd:151-178` `create_new()` | 初始化 `tickets = {}`（**不要**预置 0 值键，与 `consumables = {}` 口径一致） | 🟡 |
| 2 | `save_data.gd:255-286` `to_dict()` | 加 `"tickets": tickets` | 🟡 |
| 3 | `save_data.gd:290-335` `from_dict()` | 加 `out.tickets = data.get("tickets", {}) if data.get("tickets") is Dictionary else {}` | 🟡 |
| 4 | `save_data.gd:347-369` `migrate()` | 加 `4:` 分支：`tickets = {}` → `save_version = 5` | 🟠 |
| 5 | `game_constants.gd:1289` | `SAVE_VERSION: int = 4` → **`5`** | 🟠 |

**⚠️ 迁移分支是必要且不可省的**：
`migrate()` 是 `while save_version < SAVE_VERSION: match save_version:` 结构。
若只改 `SAVE_VERSION=5` 而不加 `4:` 分支，旧档会走到 `_:` 兜底分支（`save_version = SAVE_VERSION`）
**静默跳过** —— `from_dict()` 的 `.get("tickets", {})` 会给出 `{}` 默认值，**表面上完全正常**。
但一旦后续再引入依赖迁移的字段（如 `tower_progress`），就会**缺一次升级** ⇒ 必须显式写 `4:` 分支。

@export var tower_progress: Dictionary = {}
```

`to_dict()` / `from_dict()` / `migrate()` 同表处理。

#### 3.1.5 门票读写 API（建议新增，避免散落）

**建议**在 `save_data.gd` 中仿 `get_material` / `add_material` 的既有风格新增：

```gdscript
func get_ticket(ticket_id: String) -> int:
    return int(tickets.get(ticket_id, 0))

func add_ticket(ticket_id: String, amount: int) -> bool:
    var next := get_ticket(ticket_id) + amount
    if next < 0:
        return false
    tickets[ticket_id] = next
    return true
```

**⚠️ 风格必须统一**：`save_data.add_material()` 是「不足返回 false 不写入」，
而 `MaterialBag.add()` 对 `amount <= 0` **直接 return 不报错**。两套风格并存，
新 API **必须选 `save_data` 风格**（负数返回 false），否则会出现「门票扣成负数但没人发现」。

### 3.5 特殊装备（Special Equipment）—— ✅ S12 已拍板（新增特殊档）

#### 3.5.1 「特殊」的两个维度（用户已拍板：专属词缀 + 唯一性）

**维度 A —— 专属词缀（Exclusive Affix）**

- 只有该渠道（塔 / 深渊 / BOSS）能 roll 出的词缀。
- 机制上**完全复用**既有词缀池框架：
  ```
  AffixData.allowed_slots + fits_slot()          → 部位过滤（已有）
  affix.min_rarity                                → 稀有度过滤（已有）
  affix.position ("prefix"/"suffix")              → 前后缀过滤（已有）
  ```
- **新增**：`affix.source_tag`（如 `"tower"` / `"abyss_frost"` / `"boss_bone_tyrant"`）
  → `AffixRoller._collect_candidates()` 里加一条来源过滤。
- ⚠️ **命名陷阱**：`affixes/*.json` 的 `position` 是**字符串**（`"prefix"`/`"suffix"`），
  新字段 `source_tag` 也建议用**字符串**，与既有风格一致，避免类型不一致导致静默失配。

**维度 B —— 唯一性（Uniqueness）**

- 同一件特殊装备**全局只掉一次**（用户已拍板）。
- 机制：`EquipmentData.unique_group`（新增字段）
  + `save_data.unique_claimed`（新增 `Array[String]`，记已获得的 `unique_group`）
  + roll 时**先过滤已 claimed 的组**，全被领完则降级为普通掉落。

#### 3.5.2 ⚠️ 唯一性与「可重复刷」的冲突（✅ 已定）

**④ 底材 `rarity_min`/`rarity_max` 区间**

实测 62 件底材的现行分布：

```
('common','legendary') ×19  ('legendary','legendary') ×6   ('magic','legendary') ×5
('rare','legendary')   ×3   ('common','magic') ×1          ('mythic','mythic') ×2
('common','rare')      ×6   ('set','set') ×18              ('hidden','hidden') ×2
```

⇒ **没有任何底材的 `rarity_max` 覆盖 8 / 9** ⇒ 特殊档即使被 roll 出来，
`LootRoller._pick_template():164` 的 `if rarity < template.rarity_min or rarity > template.rarity_max: continue`
**会把全部底材筛掉** ⇒ `pool.is_empty()` ⇒ **返回 null** ⇒ **静默不掉任何东西**。

🔴 **这是最隐蔽的坑**：`_pick_template()` 空池返回 `null`，调用方若不检查就静默失败。
⇒ **必须新增专属底材**（建议 `data/equipment/special_abyss.json` / `special_tower.json`），
其 `rarity_min = rarity_max = 对应特殊档`。

**⑤ 存档兼容**

`EquipmentInstance.to_dict()` 存的 `rarity` 是 int（`:229` `clampi(..., 0, RARITY_COUNT - 1)`），
旧档不会有 8/9 值 ⇒ **向后兼容，无需迁移**。
⚠️ 但**若将来 `RARITY_COUNT` 变小**（如回退方案），旧档的 8/9 会被 `clampi` 压到 7 ⇒ 变成隐藏装。
⇒ 因此 **S12 一旦落地就不可回退**，需在文档中标记为**不可逆决策**。

**① Q-a —— 不吃越级惩罚**

`loot_table.gd:112` 的条件 `if apply_overlevel_penalty and i >= EPIC and i <= MYTHIC`
区间 `[3, 5]` **天然不含 8/9** ⇒ 特殊档不吃惩罚，**行为已正确**。

⚠️ 但这是**寄生于区间上下界的隐式行为**，不是显式声明。若将来有人把区间改成 `i >= EPIC`（去上限），

```gdscript
# game/resources/loot_table.gd:112
- if apply_overlevel_penalty and i >= EPIC and i <= MYTHIC:
+ if apply_overlevel_penalty and i >= EPIC and i <= MYTHIC and i < SPECIAL_ABYSS:
+     # 显式排除特殊档（S12 · Q-a：来源固定，与等级无关）
```

**设计理由**：特殊档的来源是**固定的**（深渊副本 / 爬塔），与「玩家当前等级 vs 装备等级」无关。
玩家 20 级去刷塔第 1 层拿到塔装，不该因为「越级」被削。⇒ 不吃是正确的，只需把这条规则**写进代码**。

| 项 | 值 |
|---|---|

**为什么必须做「半重铸」而不是复用整件重铸**：特殊装的价值核心是**专属词缀**（用户已拍板的「专属词缀 + 唯一性」）。
整件重铸会把好不容易抽到的专属词缀洗掉 ⇒ **玩家不敢重铸** ⇒ 系统无人使用 ⇒ 落入「**生成但没人消费**」陷阱。
半重铸正好保护专属词缀。

🔴 **最危险的实现路径警告**：特殊档**不能**简单地「加进 `mythic_reroll_controller` 的允许列表」——
那会得到「整件重铸把专属词缀一起洗掉」的**反向结果**。必须**显式排除** 8/9，走独立的 `special_reroll_controller`。

**UI 影响**：需新增「半重铸」入口面板 —— 7 个词缀槽 + 每槽一个锁定开关 + 锁定数上限 4 实时校验 +
专属词缀槽显示为「已锁定/不可锁」（建议图标角标加来源标记）。
⚠️ 若只做数据不做 UI ⇒ 玩家无法使用 ⇒ 又是「生成但没人消费」。

**三项的连带闭环（Q-b × Q-c 的组合收益）**
