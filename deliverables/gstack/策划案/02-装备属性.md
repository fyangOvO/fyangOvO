**核心公式**

```
词缀数值   Value(iLvl) = Base × (1 + 0.085 × (iLvl - 1)) × 品质系数 [× 1.5 若强化]
底材主属性 Stat(iLvl)  = S0  × (1 + 0.12  × (iLvl - 1))
需求等级   required    = max(1, iLvl - 2)
```

> 注意两条缩放系数**不同**：词缀 `0.085` 远低于底材 `0.12`。
> ⇒ 高 iLvl 时底材主属性增长快于词缀，词缀占比随等级**稀释**。见 §5.3。

**⚠️ 新发现（A4 断言捕获）**：
`add_skill_level`（`min_rarity=3`）出现在 `weapon_generic`（9 条）与 `jewelry_generic`（22 条）**两个通用池**中。
⇒ 与 §4.4 约束 **C3**（`min_rarity >= 3` 的词缀不得进通用池）冲突。
**裁定**：鉴于 `add_skill_level` 权重仅 **12**（全表最低），实际出现概率已极低，且技能等级是**设计上的稀有感**，**保留现状**——但把 C3 从「硬约束」降级为「软建议」，并在验证脚本中改为**警告级**（见 §8.3 V4 修订）。
> 理由：C3 的本意是防止通用池被高端词缀污染，但 `add_skill_level` 的低权重已达成同一效果；强行移出反而使「任何部位都可能出技能等级」这一**设计意图**失效。

### 1.7 结算管线现状（`stat_calculator.gd` 全文实读）

`calculate(level, equipped, buffs)` 三阶段：

```
① flat 汇总   base_stats(level) + sum_equipment() + SetSystem + HiddenGrowth + buff.flat
② pct  汇总   白名单键（pct_ 前缀 / 显式列表 / _resist 后缀）
③ 主属性三件套  max_hp / attack / armor 各按 (1 + (pct_xx + all_attributes)/100) 乘算
④ direct 映射  27 个键逐个取值（无计算，只是搬运）
```

- `FINAL_KEYS` = **26 普通键 + 5 局内键**（`armor_pierce` / `life_steal` / `damage_taken` / `regen_pct_hp` / `shield_pct_hp`）
- `BASE_GROWTH` = `flat_hp [150, 0.11]` / `flat_attack [12, 0.10]` / `flat_armor [6, 0.10]`
- ⚠️ `FINAL_KEYS` 含 `elemental_damage`，但**不含** `armor_penetration` / `skill_level` / `echo_strike`

```gdscript
    if fx_id.is_empty():
```

## 五、数值区间设计（目标三）

### 5.1 现有权重分布诊断

```
防御系权重：flat_hp 130 > flat_armor 115 > pct_attack 100 = max_resource 100
            > crit_chance 90 > crit_damage 85 > atk_speed 80 = elemental_damage 80 = dodge 80

```

**问题**：
1. **无阶梯**——权重从 130 线性滑到 12，缺乏「常见/少见/稀有」三档分明的层次
2. **`skill_level` w12 过低**——按 4 池权重总和约 500 计，单条概率 ≈ 2.4%，与紫装以上 5–7 条词缀组合后仍极难出现；**但第一步 §5.3/§10.3 明确「满技能等级 DPS 会突破上限，是设计意图，获取难度必须足够高」** ⇒ **保持低权重是对的**，不改
3. **`elemental_damage` w80 与 `dodge` w80 同权**——但前者影响 5 系 Build 全局，后者只影响生存，性价比不对等

### 5.2 新权重阶梯（三位阶）

### 5.3 强度曲线与稀释问题

**⚠️ 已识别的数值隐患**：两条缩放系数差异导致词缀占比随 iLvl **稀释**。

```
iLvl=1   词缀系数 1.000   底材系数 1.000   →  比值 1.00
iLvl=10  词缀系数 1.765   底材系数 2.080   →  比值 0.85
iLvl=20  词缀系数 2.615   底材系数 3.280   →  比值 0.80
iLvl=40  词缀系数 4.315   底材系数 5.680   →  比值 0.76
```

⇒ **高 iLvl 时底材主属性主导，词缀相对变弱**。这是**特性还是缺陷？**

| 解读 | 结论 |
|---|---|
| 若意图是「高等级装备靠底材质量」 | 现状正确，无需改 |
| 若意图是「词缀决定装备强度」 | 需把 `0.085` 提到 `0.11`–`0.12` |

**本步裁定**：**保持 `0.085` 不变**。理由：
- 词缀**条数**随稀有度增加（白 0 → 红 7），条数增长已补偿单条稀释
- 提高 `0.085` 会使红装强度非线性爆炸（7 条 × 高系数）
- 该常数被 `verify_*` 断言锚定，改动成本高、收益不明

**验证方法**：第四步数值模型做全等级曲线推演时复核。**本步只记录，不改。**

### 5.4 需求等级与 iLvl 的错位

```
required_level = max(1, iLvl - 2)
```

⇒ 掉落物 iLvl 20 的装备，15 级可穿（提前 5 级）。这是**设计意图**（`ITEM_REQ_LEVEL_OFFSET = 2` 注释明确）。
**但**：若掉落 iLvl 分布未定义，可能出现「5 级玩家掉 iLvl 40 装备」——**见 §6.3 掉落 iLvl 分布设计**。

```gdscript
+ var base := _player.get_attack_damage() * data.multiplier \
+     * (1.0 + SkillData.LEVEL_MULT_PER_LEVEL * float(eff_level - 1))
```

**⚠️ 前置依赖**：技能等级**必须持久化**（每技能各自的等级）⇒ 需 `SkillProgress` 存档段。
**⚠️ 本步范围界定**：本步只做 **「装备 `+技能等级` 词缀生效」**这一最小闭环——即 `skill_level` 词缀直接加在**技能基础等级**上。
**技能基础等级的成长（用技能点升级）** 属第一步 §9 技能解锁体系，**另行落地**。

**⚠️ 硬约束**：`add_skill_level` 的 `scales_with_item_level = false` ⇒ 在任何 iLvl 下都只 +1。这是**设计意图**（技能等级是稀缺资源），保持。

### 7.4 修复 1-4 · `cooldown_reduction` / `skill_cost_reduction` 接线 + 语义统一

**接线**：

```gdscript
# skill_controller.gd try_cast()
+ var cdr := clampf(_player.get_combat_stat("cooldown_reduction"), 0.0, 70.0)
+ var cost_red := clampf(_player.get_combat_stat("skill_cost_reduction"), 0.0, 70.0)

- if mana == null or not mana.try_spend(data.mana_cost):
+ var real_cost := data.mana_cost * (1.0 - cost_red / 100.0)
+ if mana == null or not mana.try_spend(real_cost):
      return false

- _cooldowns[id] = data.cooldown
+ _cooldowns[id] = data.cooldown * (1.0 - cdr / 100.0)
```

**⚠️ 70% 硬顶的理由**：两个值都是**乘区**，无上限会导致 100% 冷却减免（技能无 CD）⇒ 游戏性崩塌。
参照同类 ARPG：**减耗 / 减 CD 上限 70%** 是行业惯例（剩余 30% 保留核心节奏）。

**⚠️ 与第一步符文的语义统一**：`01-runes.json` 的 `cooldown_pct` / `mana_cost_pct` 与工程 `*_reduction`
**两个方向相反**（`pct` 是「延长」还是「减少」未定义）。**裁定**：

| 符文语义 | 工程语义 | 统一后 |
|---|---|---|
| `cooldown_pct: -20` | `cooldown_reduction: 20` | 符文 `cooldown_pct` 为**带符号增量**，正值 = 延长，负值 = 缩短；合并时 `total_reduction = gear_reduction - rune_cooldown_pct_sum` |
| `mana_cost_pct: -15` | `skill_cost_reduction: 15` | 同上 |

⇒ **需在 `01-runes.json` 的 `_meta.modifier_semantics` 中补一句「`*_pct` 为带符号增量，正值延长」**。
**该修正本步一并落**（属口径统一，非新增设计）。

- `TextureRect` 须设 `texture_filter = CanvasItem.TEXTURE_FILTER_NEAREST`
  （铁律：像素风禁线性过滤），并设 `custom_minimum_size = Vector2(SET_EMBLEM_SIZE, SET_EMBLEM_SIZE)`。
- **`SET_EMBLEM_SIZE` 必须与素材实际尺寸一致**。实测素材为 **48×48**，故改 48；
  若保留 16 会把徽记压糊（像素风下非整数缩放尤其明显）。
- 贴图可能为 `null`（素材缺失 / 玩家覆盖目录异常）⇒ **必须判空后再 `add_child`**，
  否则标题行左侧留空洞且 `TextureRect.texture == null` 不报错（静默失败）。参考铁律「素材缺失静默返回 null」。

**回归断言须同步更新（重要）**

`game/tools/verify_set_system.gd:187` 的断言脆弱地依赖「标题行 `get_child(0)` 是 `Label`」：

```gdscript
# 现状（改标题行结构后会崩：Invalid access to property 'text' on Nil）
_ok("首行标题含 x/6", (first.get_child(0) as Label).text.contains("2/6") or ...)
```

改为「在 `get_child(0)` 的子树里找 `Label`」，并**新增一条徽记断言**：

```gdscript
# 新增：消费点有效性 —— 素材存在时首行必须挂上非空贴图
_ok("首行徽记已挂贴图", <head 子树中存在 texture != null 的 TextureRect>)
```

> ⚠️ 这一条是本决策的**验收核心**：只断言「面板渲染出 3 套行」无法证明徽记真的显示了
> （正是 §B.1.3 发现③「生成但没人消费」能长期潜伏的原因——回归全绿但画面上什么都没有）。

**验收方式**：① 无头跑 `verify_set_system` 全绿；② **真渲染抓图目视确认套装面板左侧出现徽记**
（铁律：改 UI 素材/结构后必须真渲染抓图，无头测试只断言控件存在）。

### B.7.2 决策 2 · 套装 18 件独立图标 → 细化方案

### B.9 本轮方法论教训（写入记忆）

> **只看文件系统 / 目录列表得出的「素材缺失」结论，三次全错。**
>
> | 首轮结论 | 实际 | 错因 |
