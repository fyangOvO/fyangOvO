## 一、現狀基線（改前必須知道的事實）

### 1.1 引擎現有能力（已實現，可直接複用）

| 能力 | 落點 | 說明 |
|---|---|---|
| 技能定義 | `resources/skill_data.gd` | 13 欄位：id / display_name / slot / type / multiplier / element / cooldown / mana_cost / range / radius / dash_distance / knockback / description |
| 施放管線 | `scripts/combat/skill_controller.gd` | 冷卻檢查 → 法力檢查 → 扣費 → 按 type 分派（`try_cast()`） |
| 命中結算 | 同上 `_hit()` | `get_attack_damage() × multiplier` → `DamageCalc.compute_hit()` 完整管線（暴擊 / 元素 / 破甲 / 抗性 / 減傷） |
| 屬性讀取 | `PlayerController.get_combat_stat(key)` | 通用鍵值讀取器，注入優先 / 回退基準 |
| 技能欄 | `skill_controller._equipped_skill_ids()` | 3 個出戰位；取欄鏈 = 存檔 `skill_bar` → 職業默認欄 → 戰士默認欄 |
| 職業技能池 | `data/classes/classes.json` | 戰士 5 / 弓箭手 4 / 法師 5 |
| 圖標映射 | `game_constants.gd:1274 SKILL_ICON` | 12 技能 → 8 張圖標（多技能共用） |
| 傷害埋點 | `scripts/core/combat_metrics.gd` | 每次施放的命中數 / 放空數 |

### 1.2 三個必須先修的缺口

**缺口 ①：`skill_level` 是死鉤子（P0 級）**
- `data/affixes/attack.json:94` 有詞綴 `add_skill_level`（`stat_key = "skill_level"`，值 1–2，權重 12）
- 該詞綴已進 4 個池：`weapon_offense` / `weapon_caster` / `weapon_generic` / `jewelry_generic`
- `data/equipment/jewelry.json:108` 已有裝備帶 `"skill_level": 2.0`
- `game_constants.gd:1326` 有常量 `STAT_SKILL_LEVEL`
- **但全項目零消費**——`SkillController._hit()` 用的是寫死的 `data.multiplier`
- ⇒ 玩家穿上「+2 技能等級」的裝備，**什麼都不會發生**。這與 README §9「缺陷 F」是同一個模式（占位樁偽裝成計劃中）。

**缺口 ②：技能元素寫死**
- `_hit()` 直接把 `data.element` 傳給 `DamageCalc`
- `skill_data.gd:41` 註釋寫「屆時由裝備/狀態改寫本字段」——**該改寫從未實現**
- ⇒ 「火系法杖放出的火球」與「冰系法杖放出的火球」完全一樣。

**缺口 ③：形態只有 3 種，且名不副實**
- `SkillType` 只有 SINGLE(0) / AOE(1) / DASH(2)
- 「單體」實為**瞬間命中扇區內最近目標**（`find_targets_in_arc` 取 `targets[0]`），**無飛行彈道**
- `lightning_chain` 名為「閃電鏈」但**無任何連鎖邏輯**，就是個普通單體
- ⇒ 弓手的「遠程」體驗與戰士無異，法師的「元素掌控」也沒有體現。

## 二、延展機制設計

### 2.1 機制 A · 技能等級（Skill Level）

**定位**：讓「+技能等級」這條裝備詞綴真正生效，並成為裝備驅動的核心乘區之一。

| 項 | 設計 |
|---|---|
| 等級範圍 | **1–10**（基準 1，上限 10） |
| 作用域 | **全局**（`skill_level` 是所有技能共享的等級，非單技能獨立等級） |
| 來源 | ① 裝備詞綴 `add_skill_level`（既有，1–2）② 天賦大節點「技之極意」+1（新增）③ 傳奇特效 2 件（新增：+2 全技能 / +3 單技能）④ 局內三選一新增選項「技之領悟」+1（見 §7.4） |
| 生效公式 | `effective_multiplier = base_multiplier × (1 + 0.08 × (level - 1))` |
| 數值錨點 | L1 = ×1.00 ｜ L4 = ×1.24 ｜ L7 = ×1.48 ｜ **L10 = ×1.72** |
| **不影響** | 冷卻、藍耗、範圍 —— 避免與既有 `cooldown_reduction` / `skill_cost_reduction` **雙重計入** |
| 消費點 | `SkillController._hit()` **唯一一處** |
| 新介面 | `PlayerController.get_skill_level() -> int`（注入優先 / 回退 1） |

> **為何全局而非單技能**：單技能等級需要 36 個獨立計數器 + 一套加點 UI，成本高且與天賦樹職責重疊。
> 全局等級讓「+2 技能等級」成為一個乾淨的乘區，裝備一眼可懂。若日後需要精細化，再擴為 `{skill_id: level}` 字典。

### 2.2 機制 B · 符文改造（Rune）

**定位**：技能行為改造，提供構築深度。符文是**掉落物**，可自由拆裝（零成本），鼓勵實驗。

| 項 | 設計 |
|---|---|
| 符文槽 | 每個技能 **3 槽** |
| 解鎖條件 | 技能等級達 **3 / 6 / 9** 時解鎖第 1 / 2 / 3 槽 |
| 鑲嵌成本 | 免費（拆卸也免費）；同一符文可被多技能共用（**符文是圖鑑式解鎖，非消耗品**） |
| 適用限制 | 每個符文聲明 `allowed_types`（如「穿透」僅對 PROJECTILE 有效）；不匹配的槽位在 UI 中灰顯 |
| 互斥 | 同類符文互斥（如「穿透」與「分裂」不可同插） |

### 2.3 機制 C · 形態分支（Form Branch）

**定位**：終極方向選擇，一技能一抉擇，可在據點重置（成本 = 500 金幣）。

| 項 | 設計 |
|---|---|
| 解鎖 | 技能等級達 **5** 時二選一 |
| 重置 | 據點技能面板，500 金幣 / 次 |
| **設計策略** | **按形態模板定義，不逐個技能手寫** —— 7 個模板覆蓋全部 36 技能 |

**分支模板（7 套）**

| 技能形態 | 分支 A | 分支 B |
|---|---|---|
| SINGLE 單體 | **專注**：倍率 +40% | **連擊**：追加一段 60% 傷害 |
| AOE 範圍 | **擴張**：半徑 +40% | **滯留**：留下 3 秒持續區域（50% 傷害 / tick） |
| DASH 位移 | **貫穿**：距離 +50%，路徑傷害 +30% | **餘像**：衝刺後留下 2 秒殘影持續攻擊 |
| PROJECTILE 投射物 | **銳鋒**：穿透 +2 | **散射**：改為 3 枚扇形（每枚 70%） |
| GROUND 持續區域 | **深潭**：持續時間 +50% | **湧動**：每 1 秒脈衝一次額外傷害 |
| SUMMON 召喚 | **軍團**：召喚數 +1 | **精銳**：召喚物傷害 +60% |
| BUFF 增益 | **持久**：持續時間 +50% | **強化**：效果 +40% |

> 此設計讓「36 技能 × 2 分支 = 72 變體」退化為「**7 模板 × 2 = 14 條規則**」，實作成本大幅下降，且行為一致、易於平衡。

## 三、新增技能形態（4 種）技術定義

### 3.1 SkillType 枚舉擴充

```gdscript
enum SkillType {
    SINGLE = 0,      ## 單體：朝向前方扇區內最近的 1 個目標（既有）
    AOE = 1,         ## 範圍：以玩家為中心 radius 內全部目標（既有）
    DASH = 2,        ## 位移：沿朝向衝刺並擊退撞到的目標（既有）
    PROJECTILE = 3,  ## 投射物：發射飛行彈道，命中結算（新增）
    GROUND = 4,      ## 持續區域：地面生成區域實體，每 tick 結算（新增）
    SUMMON = 5,      ## 召喚：生成友方召喚物，獨立 AI（新增）
    BUFF = 6,        ## 增益：對自身施加增益 / 護盾（新增）
}
const TYPE_NAMES: Array[String] = ["單體", "範圍", "位移", "投射物", "持續區域", "召喚", "增益"]
const TYPE_KEYS: Array[String] = ["single", "aoe", "dash", "projectile", "ground", "summon", "buff"]
```

### 3.2 各形態實作要點

| 形態 | 新增檔案 | 核心邏輯 | 複用 |
|---|---|---|---|
| PROJECTILE | `scenes/combat/projectile.tscn` + `scripts/combat/projectile.gd` | `speed` / `max_range` / `pierce_count` / `hit_set`（防重複命中）；命中調 `SkillController._hit()` | `HitQuery`、`DamageCalc` |
| GROUND | `scenes/combat/ground_area.tscn` + `scripts/combat/ground_area.gd` | `impact_multiplier`（落地一次性伤害，可选，默认 0）/ `duration` / `tick_interval`；半径内按 tick 结算，到期自动释放 | `HitQuery.find_in_radius` |
| SUMMON | `scenes/combat/summon.tscn` + `scripts/combat/summon.gd` | 複用 `EnemyBase` 的狀態機，**改為友方**（攻擊 `enemies` 組）；`lifetime` 到期消失 | `EnemyBase` AI、`HealthComponent` |
| BUFF | 無新場景 | 直接寫入 `RunBuffSystem` 的 buffs 字典（格式已有：`{buff_id: {"pct": {...}}}`） | `RunBuffSystem`、`StatCalculator` |

> **SUMMON 的關鍵風險**：`EnemyBase` 的目標查找寫死為「找 `player` 組」。
> 需抽出 `target_group` 參數（默認 `player`，召喚物用 `enemies`），並確認召喚物**不被玩家技能誤傷**（`HitQuery` 需排除 `summons` 組）。

## 五、數值規範

### 5.1 統一標尺：DPS 係數

**DPS 係數 = multiplier ÷ cooldown**（單位：AD/s，即「每秒貢獻多少倍攻擊力」）

現有 12 技能實測區間：

| 技能 | 倍率 | 冷卻 | DPS 係數 | 判定 |
|---|---|---|---|---|
| `power_strike` | 5.0 | 8.0 | 0.625 | 上限參考 |
| `cleave` | 3.5 | 6.0 | 0.583 | ✅ |
| `spin_slash` | 1.4 | 3.0 | 0.467 | ✅ |
| `piercing_shot` | 2.2 | 4.5 | 0.489 | ✅ |
| `fireball` | 2.4 | 4.0 | 0.600 | ✅ |
| `lightning_chain` | 1.8 | 5.5 | 0.327 | ⚠️ 偏低 |
| `venom_shot` | 1.6 | 5.0 | 0.320 | ⚠️ 偏低 |
| `frost_nova` | 1.1 | 5.0 | 0.220 | ❌ 過低 |
| `arrow_rain` | 1.0 | 6.0 | 0.167 | ❌ 過低 |
| `dash_strike` | 1.0 | 8.0 | 0.125 | 位移技，不適用 |
| `shadow_blink` | 1.2 | 9.0 | 0.133 | 位移技，不適用 |

**設計區間（硬約束）**

| 技能類別 | DPS 係數區間 | 備註 |
|---|---|---|
| 傷害技能（單體 / 範圍 / 投射） | **0.40 – 0.70** | 超出上限須有明確代價（長冷卻 / 高藍耗 / 條件觸發） |
| 持續區域（GROUND） | 0.45 – 0.75 | 以「總傷害 ÷ 冷卻」計（含全部 tick） |
| 位移技能（DASH） | 0.10 – 0.20 | 主要價值在位移，傷害為輔 |
| 增益 / 召喚（BUFF / SUMMON） | — | 不適用；以「等效增益幅度」衡量 |

> **推論**：3 個出戰技能的 DPS 係數合計 ≈ **1.2–2.0**，加上普攻（基準 1.0）⇒ 總 DPS ≈ 2.2–3.0 AD。
> 與 GDD 的綜合係數 `SkillMult L1 = 1.8 → L20 = 2.8` 吻合，**本規範與 GDD 一致**。

> ⚠️ **GROUND 技能的計算口徑（易錯點，設計時踩過）**：§4 表格中 GROUND 技能的「倍率」欄是**每 tick 倍率**，
> 「DPS 係數」欄才是 **總傷害 ÷ 冷卻**。換算式：
> `DPS 係數 = (impact_multiplier + multiplier × (duration ÷ tick_interval)) ÷ cooldown`
> （`impact_multiplier` = 落地一次性傷害，可選，默認 0）
> 例：`thunder_storm` = (0 + 0.8 × (4.0 ÷ 0.5)) ÷ 9.0 = 6.4 ÷ 9 = **0.711** ✅
> 例：`meteor` = (3.0 + 0.5 × (3.0 ÷ 0.5)) ÷ 10.0 = 6.0 ÷ 10 = **0.600** ✅
> 同理 PROJECTILE 多發技能（`multishot` / `shadow_volley`）的「DPS 係數」按**全中**計算：
> `multishot` = 1.0 × 3 ÷ 4.5 = **0.667** ✅
>
> **校驗工具**：`01-check_skill_dps.py`（已跑通，27 條傷害技能全過，退出碼 0）。
> 落庫時應把該邏輯移植為 GDScript 斷言（見 §7.3 V9）。

### 5.2 倍率分檔

| 檔位 | 倍率 | 冷卻 | 藍耗 | 典型 |
|---|---|---|---|---|
| 輕 | 1.4 – 2.0 | 3.0 – 4.5 | 15 – 22 | 旋刃、冰霜新星、寒冰箭 |
| 中 | 2.0 – 2.8 | 4.5 – 6.0 | 16 – 28 | 裂斬、火球術、爆裂箭 |
| 重 | 3.0 – 4.0 | 6.0 – 8.0 | 30 – 35 | 蓄力斬（5.0 為特例，代價是 8 秒冷卻） |
| 終極 | 5.0 – 6.0 | 10.0 – 15.0 | 40+ | 隕石術 |

**藍耗公式**（便於新技能取值）：`mana_cost ≈ multiplier × 8`（±20% 浮動）
驗證：cleave 3.5×8 = 28（實際 30 ✅）｜fireball 2.4×8 = 19.2（實際 18 ✅）｜power_strike 5.0×8 = 40（實際 35 ✅）

### 5.3 技能等級的平衡影響

L10 時倍率 ×1.72。以 `cleave` 為例：3.5 → **6.02**，DPS 係數 0.583 → **1.003**。
⇒ **滿技能等級的單技能 DPS 係數會突破 1.0 上限**，這是設計意圖（技能等級是頂級養成目標），
但需注意：**全身 +技能等級 裝備的獲取難度必須足夠高**（詞綴權重 12，為最低檔之一；傳奇特效 +2/+3 為神話級）。

### 11.2 槽位分配策略（3 槽 = 3 個互斥組選擇）

3 個符文槽，每個符文屬於 4 個互斥組之一（`form` / `element` / `amp` / `util`）。
同組符文**不可同時插入同一技能**。因此最優配置天然是：

| 槽 | 建議組 | 說明 |
|---|---|---|
| 槽 1 | `form` 或 `element` | 決定技能**行為方向** |
| 槽 2 | `element` 或 `amp` | 補元素或補數值 |
| 槽 3 | `util` | 附加效果 |

⇒ 玩家**無法同時**拿到「改形態 + 改元素 + 改數值 + 加效果」全部四項，
必須取捨——這正是設計要的構築深度。

## 十四、特效與動畫需求

### 14.1 玩家動作素材：**需補齊**（2026-09-24 用戶否決原「零新增」決策）

> ❌ **已作廢**：原結論為「技能施放複用 `attack`，玩家精靈素材零新增」，
> 理由是「省下 3×8×6 = 144 幀」。
> **用戶 2026-09-24 明確否決**，原話：
> 「**不需要節省素材，需要動畫流暢；之前運行人物轉變很尷尬，需要細化素材**」。
> ⇒ 成本控制不再作為此處的決策依據，**改以「動作是否自然」為準**。

**問題不是「有沒有施法動作」這麼簡單，而是一組動作覆蓋度缺口。**實測三職業素材現狀：

| 動作 | 方向覆蓋 | 幀數 | 診斷 |
|---|---|---|---|
| `idle` | **僅 `s`** | **1** | ⚠️ 站著不動時**永遠正面朝鏡頭**，走完路停下就「啪」地轉正 |
| `walk` | 8 方向 | 4 | 方向齊全；4 幀 @12fps = 0.33s/循環，步態偏急 |
| `attack` | 8 方向 | 4 | 方向齊全；4 幀揮砍，重量感不足 |
| `cast` | — | **0** | ⚠️ 法師丟火球卻做**劈砍**動作 |
| `hurt` | **僅 `s`** | 2 | ⚠️ 側面/背面受擊 → 瞬間「轉正」 |
| `death` | **僅 `s`** | 4 | ⚠️ 側面/背面死亡 → 瞬間「轉正」後倒地 |

**「轉向尷尬」的程式根因**（`enemy_base.gd` + `player_controller.gd`，已核實）：

1. `resolve_clip()`（`enemy_base.gd:612`）按 `ANIM_FALLBACK` 逐級回退，
   某方向缺幀時**硬回退到首個可用方向**（此處即 `s`），不做任何插值或翻轉補償。
2. `_apply_facing()`（`player_controller.gd:782`）的左右翻轉**只在 `_clips.is_empty()` 時生效**
   —— 也就是**占位美術階段**。一旦接入真素材，翻轉完全關閉。
   ⇒ **沒有哪個方向，就是硬缺哪個方向**，沒有兜底。
3. `idle` 只有 1 幀 ⇒ 連「呼吸」都沒有，角色像貼圖立牌。

⇒ **結論：素材覆蓋度是唯一的解法**，程式層已無補償空間（也不應該加旋轉/縮放補償，
美術規範 §1.1 明令禁止運行時旋轉）。

詳細的補齊方案（含「一般 / 細化」兩檔）見 **附錄 A · 素材需求（兩方案）**。

## A.1 為什麼必須補素材（「轉向尷尬」根因診斷）

用戶 2026-09-24 原話：「**不需要節省素材，需要動畫流暢；之前運行人物轉變很尷尬，需要細化素材**」。

這個「尷尬」不是感覺問題，是**素材覆蓋度 + 程式回退規則**共同造成的，三條根因：

| # | 根因 | 程式位置 | 現象 |
|---|---|---|---|
| 1 | `idle` 只有 `s` 方向**一幀** | `assets/pack/creatures/*/char_*_idle_s_01.png` | 站著不動**永遠正面朝鏡頭**；走完路停下 → 瞬間轉正 |
| 2 | `resolve_clip()` 對缺失方向**硬回退首個可用方向**，無插值無補償 | `enemy_base.gd:612`（`ANIM_FALLBACK`） | 朝北走完停下 → 顯示正面；側面受擊 → 顯示正面受擊 |
| 3 | `_apply_facing()` 的左右翻轉**只在 `_clips.is_empty()`（占位美術）時生效** | `player_controller.gd:782-789` | 真素材接入後翻轉完全關閉 ⇒ **缺哪個方向就是硬缺** |
| 4 | **完全沒有 `cast` 動作** | `PACK_ACTIONS` 不含 `"cast"`（`enemy_base.gd:496`） | 法師丟火球卻做**劈砍**動作 |

> ⚠️ **程式層已無補償空間**：`_apply_facing()` 的翻轉不能重新開啟（有真素材時翻轉會把西向幀鏡像成東向，
> 方向全錯）；美術規範 §1.1 也**明令禁止運行時旋轉**（破壞像素網格）。

### 製作方向指引（一般方案）

| 動作 | 幀序設計（4 幀） | 要點 |
|---|---|---|
| `idle` | ① 中立 → ② 吸氣（上身 +1px、肩微抬）→ ③ 中立 → ④ 吐氣（上身 −1px） | **上下 1–2px 起伏即可**，不要左右晃；武器/披風錯後 1 幀擺動 |
| `cast` | ① 起手（武器/手抬至胸前）→ ② 蓄力（後傾 1px、能量匯聚）→ ③ **釋放**（前傾 1px、武器前送）→ ④ 收勢（回到接近中立） | 第 ③ 幀是關鍵：**與 `attack` 的區別就在這裡** —— `attack` 是橫向劈砍，`cast` 是**向前推**。法師/弓箭手尤其明顯 |

## A.4 細化方案 · 玩家精靈（追求流暢與演出感）

**目標**：動作有重量感與過渡，不再是「4 幀卡頓」。**含一般方案全部內容**。

| 動作 | 方向 | 幀/方向 | 小計 | 新增 | 相對一般方案 |
|---|---|---|---|---|---|
| `idle` | 8 | 6 | 48 | **+47** | 4 → 6 幀，加「呼吸停頓」與武器微擺 |
| `walk` | 8 | 6 | 48 | **+16** | 4 → 6 幀，做「抬腳–過渡–落地」三段式 |
| `attack` | 8 | 6 | 48 | **+16** | 4 → 6 幀，加**預備動作**（起手後拉）與**收勢** |
| `cast` | 8 | 6 | 48 | **+48** | 4 → 6 幀，加蓄力粒子幀與釋放餘韻 |
| `hurt` | 8 | 3 | 24 | **+22** | 2 → 3 幀，加「僵直幀」讓受擊有分量 |
| `death` | 8 | 6 | 48 | **+44** | 4 → 6 幀，加「倒地彈一下」與塵土過渡 |
| **合計** | | | **264** | **+193 / 套** | |

**⇒ 3 職業合計新增 579 幀**（目標總量 264 × 3 = 792 幀）

### 製作方向指引（細化方案 · 相對一般方案的增量）

| 動作 | 6 幀結構 | 為什麼更流暢 |
|---|---|---|
| `idle` | 中立 → 吸氣 → 吸氣頂點（**停 1 幀**）→ 中立 → 吐氣 → 吐氣底點（**停 1 幀**） | 加停頓後呼吸有「節奏」而不是機械往復 |
| `walk` | 觸地 → 承重 → 抬腳 → **過渡（跨步中點）** → 前伸 → 落地 | 4 幀是「兩拍」，6 幀才能做出**抬–過渡–落**三段，步態不再急 |
| `attack` | 起手 → **預備（後拉，蓄勢）** → 發力 → 命中 → 收勢 → 中立 | 預備幀讓揮砍有「重量」；收勢幀讓連招不突兀 |
| `cast` | 起手 → 蓄力 → 蓄力頂點 → 釋放 → **餘韻（後座）** → 收勢 | 蓄力頂點 + 餘韻讓施法有「輸出感」 |
| `hurt` | 後仰 → **僵直（不動 1 幀）** → 回復 | 僵直幀讓受擊有「被打到」的實感 |
| `death` | 後仰 → 跪倒 → **觸地彈起** → 側倒 → 落地 → 靜止 | 觸地彈一下是「死亡演出」的關鍵細節 |

> ⚠️ **細化方案需要一項程式改動**：目前**整套精靈共用一個 `fps = 12.0`**（`dnf_load_names` 硬編碼），
> 無法讓 `walk` 用 15fps、`attack` 用 18fps。
> ⇒ 若要分動作調速，需改 `enemy_base.gd` 讓 `fps` 可按動作覆寫（**約 5–10 行**）。
> 若不想改程式：**統一 12fps 也能用**，只是流暢度靠幀數而非幀率換來。
